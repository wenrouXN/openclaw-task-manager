# 反模式详解 — Task Manager

## 已验证的失败模式

### 1. 先执行后补录

**案例**：2026-05-17 devengineer 执行 task-management 清理 + supervisor 修复，全程 5 步未注册任务，事后被老大发现要求补录。

**后果**：中间状态丢失、无法恢复、无法追溯做了什么。

**识别信号**：执行到第 3 步时想到"好像应该建个任务"但没停下来。

**正确做法**：闪过念头 → 立即停下 → create → 再继续。

### 2. 口头说要落盘但直接动手

**案例**：脑子里闪过"应该 create"的念头，但觉得"先开始吧"就跳过了。

**后果**：同上。

**识别信号**：用户请求一句话但需要动多个文件/服务。

**正确做法**：宁可多 create 一个任务（哪怕最后很快 complete），也不要漏掉。

### 3. 小看任务复杂度

**案例**："就删个旧 skill + 改个模型"→ 实际还有清 session、改引用、重建 cron。

**后果**：原本想"就改个配置"结果变成 5 步操作，过程中没有跟踪。

**识别信号**：用户请求一句话但需要动多个文件/服务。

**正确做法**：先评估步数。如果 ≥3 步，立即 create + plan。

### 4. 诊断驱动的范围蔓延

**案例**：从"supervisor 心跳 error"开始 → 发现 session 膨胀 → 发现旧 skill → 发现模型问题 → 全修了。

**后果**：做了大量操作但没有记录过程和决策。

**识别信号**：排查过程中发现了"顺便可以修"的新问题。

**正确做法**：发现新问题时暂停，评估是否扩大 scope 并更新 plan。

## 自检检查点

在执行第一个实质性操作（写文件、改 config、删东西）之前，自问：

```
□ 这个请求有 ≥3 步吗？
□ 会改 repo / config / cron / 外部服务吗？
□ 可能需要 spawn 或 ACP 吗？
□ 用户要求跟踪了吗？
□ 预计超过 5 分钟吗？
□ 是先诊断再修复的流程吗？
□ 改完需要验证才能确认成功吗？
```

**任一勾选 → 立即 create + plan，不要继续执行。**

## 事后补录规范

如果已经跳过预检开始执行了，发现时应：
1. 立即 `create` 任务
2. `plan` 填入已知步骤
3. 用 `update --last-step` 标记已完成的步骤
4. 继续执行后续步骤

事后补录不如事前注册，但比不记录好。
